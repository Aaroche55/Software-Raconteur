# Software Architecture Solo Week 2

## Stakeholders

- Original PhD Student
- Researchers
- Data analysts
- People installing the software
- Future engineers
- NASA
- Data subjects


## Quality Requirements per Stakeholders

- Researchers: Ease of install and ease of use, understantable outputs
- Future engineers: Readability, extendability
- Original Phd Student: Reproducability, documentation
- Nasa: Reusable

## Software Quality Dimensions
### Core
- Functional Suitability: The software must be capable of completing the task it was designed for. New features should continue to produce accurate results.
- Interaction Capability: Extensions should remain understandable to non-technical users. New options should have clear names, sensible defaults, and graphs that are easy to interpret without requiring users to understand the source code.

### Nice to haves
- Maintainability: The code should be divided into reusable functions, such as loading data, validating records, calculating cumulative duration, and generating graphs. This allows future engineers to add features without modifying one large block of code or accidentally affecting unrelated functionality.
- Reliability: The project should produce consistent and accurate results whenever it is run with valid data. It should handle missing or incorrectly formatted records without crashing, provide useful error messages, and generate the same output from the same input data. This is especially important when researchers rely on the results for analysis or reproduction.
